# 2026-09 codebase review — second-Kindle readiness

Written 2026-09-27 against `main` @ `a714c13` (PR #16 merged). Follows
`REVIEW_FINDINGS.md` (2026-08). Read `KITCHEN_HANDOFF.md` and
`KITCHEN_SCREEN_PLAN.md` first: this review takes their decisions as given
(native HTML→PNG at 1072×1448 rendered on the Mac, not a TRMNL recipe;
per-device alert state in `server/device-alerts.js` keyed by `?device=`). It
looks for what would still break when a second Kindle starts polling.

## How this was checked, and its limits

- Every file under `server/`, `kindle/`, `byos-recipes/`, `scripts/` and `pi/`,
  plus the deploy scripts, was read.
- `cd server && npm test` passes: 11 suites, exit 0. So does
  `./scripts/validate.sh`. To run them, node-canvas was built from source in the
  cloud container.
- Four findings were **reproduced** with scratch scripts: F1, F2, F5 and F13.
  The scripts are in the appendix and can be turned into regression tests.
- Everything else comes from reading the code. Anything that depends on the
  Paperwhite's firmware is marked **unverified**: this cloud session cannot
  reach the Pi, BYOS, either Kindle, or the LAN. None of these findings has
  been checked against live production state. CLAUDE.md says "verify a claimed
  bug against live state before fixing it", and that applies here.

## Critical

### F1 — The kitchen Kindle would be attributed to v0 and would disable v0's alarms

**Evidence**
- `kindle/fetch-dashboard.sh:297` hardcodes `${SERVER_URL}/dashboard`, and the
  client only ever appends `battery`, `charging`, `grid` and `t` (`:302-338`).
  There is no device-id setting anywhere in `kindle/`.
- `server/device-alerts.js:98-99` treats a missing `?device=` as v0. That is
  deliberate, so the desk Kindle keeps working unchanged.
- `scripts/setup-kitchen-kindle.sh:107` says "the dashboard client can be
  deployed the same way v0's is". `deploy-kindle.sh:49` ships the one
  `kindle/config/dashboard.conf`, which points at the Pi's `/dashboard`.

**Reproduced** (`misattrib.js`, appendix). Both screens poll every 10 minutes,
v0 is at 12% at 21:00, and the kitchen is at 100% and charging:

- **6 battery pings and 6 bedtime pings per hour** to Discord. Each kitchen
  reading (`charging=1`) re-arms v0's latches at `battery-alert.js:46` and
  `bedtime-alert.js`'s `chargingStatus === '1'` branch.
- With v0 dead from 07:00, the kitchen's polls keep v0's staleness state fresh.
  The result is **0 staleness alerts in 3 hours**.

This is the failure mode `device-alerts.js` was built to prevent. It is just
moved from the server into the client.

**Other ways the stock client fails on the kitchen device**
- It gets v0's 600×800 TRMNL image instead of the kitchen paper.
- `deploy-kindle.sh:59` forces password auth (`PubkeyAuthentication=no`) and
  requires `KINDLE_PASSWORD` (`:36`). The kitchen is set up for **key auth
  only** (`setup-kitchen-kindle.sh`), so the deploy script can't reach it.

**Fix**
- Add `DEVICE_ID` and `DASHBOARD_PATH` keys, and optionally `HEALTH_PATH`, to
  `dashboard.conf`. `fetch-dashboard.sh` should append `device=$DEVICE_ID`
  whenever it is set.
- Ship `kindle/config/kitchen.conf` with `DEVICE_ID=kitchen`.
- Give `deploy-kindle.sh` a `--config` option and a key-auth mode.
- Add a test: `sh fetch-dashboard.sh --dry-run -c kitchen.conf` must log a URL
  containing `device=kitchen`.
- Until this is done, **do not deploy `kindle/` to the Paperwhite**, even to
  test it.

## High

### F2 — Recurring calendar events are silently dropped

**Evidence**
- `server/calendar-service.js:88-99` maps each VEVENT to its own `start`/`end`
  and ignores `e.rrule`, `e.exdate` and `e.recurrences`.
- node-ical does not expand recurrences.
- A daily standup that started in January only ever appears on its first
  instance.

**Reproduced** (`cal-rrule.js`). Given a `FREQ=DAILY` event starting
2026-01-05 and a one-off event tomorrow, `formatForDashboard` returns
`today: []`, `tomorrow: ['One-off tomorrow']` and `upcoming: []`. The
recurring event is missing everywhere.

**Impact**
- Hidden today, because `CALENDAR_URL` is unset and the tile serves mock data
  (see F3). The moment the iCloud URL goes into `.env`, the Calendar tile
  undercounts, and iCloud calendars are heavy on recurrence.
- The kitchen's `/api/agenda` (KITCHEN_HANDOFF task 2) is built on this
  service, so this blocks that task too.

**Fix**
- In `fetchCalendarData`, expand `rrule.between(windowStart, windowEnd)` over
  roughly today−1 to today+8.
- Apply `exdate`, and replace overridden instances from `recurrences`.
- Keep each instance's duration.
- Add `calendar-service.test.js`, which doesn't exist yet (see Tests).

**Also here**
- The all-day branches (`:193`, `:202`, `:210`) compare a real UTC `Date`
  (`start`) against the shifted "local wall clock" frame (`todayStart`). This
  is only correct when the Pi's system timezone equals `config.TIMEZONE`.
- Pin that with a test, or do all comparisons in one frame.

### F3 — Fake and stale data renders exactly like live data

**Evidence**
- Every tile endpoint returns a `source` field (`fixture`, `mock`,
  `expired-cache`, `api`, `cache`). **No recipe reads it.** The only data-age
  hint on any tile is RSS's `generated`
  (`grep -n source byos-recipes/*/*.liquid` finds nothing).
- `local-dashboard-server.js:438-450` deliberately turns an unconfigured
  calendar into **mock** data.
- `calendar-service.js:61-82` mock data is "Piano tuning - Marriot 2:00 PM"
  and "Dinner with Sarah 5:30 PM" every day, with "upcoming" pinned to
  "Thu, Mar 12".
- `calendar-service.js:153` also falls back to mock when the **API fails**
  with no cache. That contradicts its own `getEmptyCalendarData` comment:
  "better a blank section than fake mock events on a real display".
- Todoist, transit, fitness and RSS all end their fallback chains in fixtures.
  In production, "API down, cache lost" shows made-up tasks and made-up
  arrivals.

**Impact**
- Per CLAUDE.md, Calendar is on mock in production right now. The Day Board's
  top-left quadrant is presumably showing invented appointments as real, but
  that is not verified against the live screen.
- Transit on `expired-cache` shows old countdowns as if they were live (F11).

**Fix, smallest first**
1. Add a reusable Liquid badge that shows `SAMPLE` when `source` is `fixture`
   or `mock`, and `as of HH:MM` when it is `expired-cache`. Put it in every
   quadrant and full variant.
2. Once real credentials exist, stop falling back to fixtures and fall back to
   an explicit empty or "unavailable" state instead. `trmnl-service.js:228-231`
   already follows the rule "never fabricates content for the real display".

### F4 — Dependency changes never get installed on the Pi

**Evidence**
- `deploy-to-pi.sh:52-57` rsyncs `server/` first. Then `:61-62` compares the
  **remote** `package.json` hash with the local one. After the rsync they are
  always equal on a Mac (`md5 -q`), so `npm install --production` never runs.
- The inline comment, "hashes match after sync, no npm install needed", reads
  as though this was the intended check.

**Impact**
- The first PR that adds or bumps a dependency deploys cleanly, then crashes
  on restart with `MODULE_NOT_FOUND`.
- `/dashboard` goes down, and so does **the alerting that would report it**,
  because the staleness timer lives in the same process (F16).
- The Kindle keeps showing `previous.png`, so from the wall this looks like a
  "stuck screen", not "server down".

**Fix**
- Take the remote hash *before* the rsync, or compare against a stamp file
  written by the last successful `npm install`.
- Better: always run `npm ci --omit=dev` when `package-lock.json` differs.

The horoscope spike in this PR deliberately adds **no** dependencies.

### F5 — Every task due today shows as OVERDUE each evening

**Evidence**
- `server/todoist-service.js:144` computes
  `today = new Date().toISOString().slice(0, 10)`, which is the **UTC** date.
- `:157` sets `isOverdue = dueDate < today`.
- From 00:00 UTC on (19:00 CDT, or 18:00 CST), "today" is tomorrow, so every
  task due today gets flagged as overdue. That is most of the 11:00–22:00
  Day & Evening playlist.

**Reproduced** (`todoist-utc.js`). At 20:00 CDT, a task due 2026-09-27 comes
out as `isOverdue: true` with `counts: {overdue: 1, today: 0}`.

**Why the tests miss it**
- Every test injects `todayIso`.
- The fixture path passes `fixture._todayIso` (`:201`).
- So today this only affects the live path, which is inactive until
  `TODOIST_API_TOKEN` lands.

**Fix**
- Derive `today` with `Intl.DateTimeFormat('en-CA', { timeZone: config.TIMEZONE })`,
  the same way `bedtime-alert.js` already does.
- Add a test with an injected 01:00Z clock.
- The kitchen's `/api/agenda` needs this fix too.

## Medium

### F6 — The kitchen can't be staleness-monitored if it polls the Mac

**Evidence**
- The only place a fetch is recorded is `handleDashboardRequest`
  (`local-dashboard-server.js:325-326`).
- In the plan's architecture, the kitchen fetches `GET /paper.png?device=kitchen`
  from the **Mac** (`KITCHEN_SCREEN_PLAN.md`, "Recommended architecture").
- The Pi therefore never sees a kitchen fetch. Adding `kitchen` to
  `MONITORED_DEVICES`, as the plan says to, would make it go stale immediately
  and alert every interval, which is the exact outcome the handoff warns
  about.

**Options**, in order of preference:

a. **Pi proxy**: add `GET /paper.png` on the Pi.
   - It records the fetch and streams the Mac's last good PNG from a disk
     cache, following the `trmnl-service.js` pattern.
   - It keeps a single server address for all Kindles and a single place for
     alerts.
   - The FileVault cold-boot problem is covered for free: the Pi serves its
     last cached paper.
   - It also removes F10's ICMP/`/health` coupling to the Mac.

b. **Heartbeat**: add `GET /api/heartbeat?device=kitchen`, which calls
   `recordFetch` and nothing else. The Kindle loop calls it after each
   successful fetch from the Mac.

c. Have the Mac render service report to the Pi. This is fragile: the thing
   being watched would be vouching for itself.

### F7 — Alert thresholds and active hours are global, not per device

- `device-alerts.js:119-126` gives every device the same `staleThresholdMs`,
  `activeHoursStart` and `activeHoursEnd` from `config.js:44-47`.
- The kitchen's morning face starts at **05:30** (plan, "The three faces").
  Global 07:00 means kitchen outages between 05:30 and 07:00 are never
  alerted.
- `StalenessAlertState.isActiveHour` only works to the hour, so 05:30 can't be
  expressed at all.
- The 45-minute threshold was tuned for v0's cadence. It needs to be at least
  twice the kitchen's roughly 20-minute poll.
- **Fix:** put optional `activeHours: {start: '05:30', end: '22:00'}` and
  `staleThresholdMs` on each `DEVICE_PROFILES` entry, merged over
  `alertConfig`, and switch the active-hours check to minutes. The existing
  26 device-alerts tests make this a safe change.
- Also make sure `config.js`'s comment "must match
  kindle/config/dashboard.conf" becomes per-device. Each Kindle's own conf is
  the source of truth for its hours.

### F8 — `/health` can't answer "is each Kindle alive?"

- `handleHealthCheck` (`local-dashboard-server.js:381-399`) reports
  `trmnl.lastScreenFetchedAt`, which is when the **Pi fetched from BYOS**.
- `KITCHEN_SCREEN_PLAN.md` ("Also noted") uses it as proof that v0 is alive.
  With `TRMNL_MODE=only` it is a decent proxy, since the Kindle's polls drive
  the BYOS fetches. It stops being one once `/next` or a second consumer
  triggers fetches.
- **Fix:** add a `devices` block built from the registry, e.g.
  `{ v0: { lastFetchAt, monitored, stale } }`. `StalenessAlertState` already
  keeps `lastFetchAt`. This is also the cheapest input for the Discord
  "status" ideas in `docs/scoping/discord-llm.md`.

### F9 — 600×800 is hardcoded in the render path

| Where | What |
|---|---|
| `server/optimize-for-eink.py:38-40` | **Resizes any input to 600×800** with LANCZOS. A 1072×1448 kitchen page run through it would be downscaled and squashed from a 0.740 to a 0.750 aspect ratio. The plan names this script as "the established treatment" for the kitchen. |
| `server/optimize-for-eink.py:82,91` | Validation checks for exactly 600×800. |
| `server/config.js:65-66` | `CANVAS_WIDTH`/`CANVAS_HEIGHT` are constants, not per device. |
| `server/dashboard-engine.js:1349-1350` | `DashboardEngine` defaults to 600×800. |
| `server/trmnl-preview.py:49` | `CANVAS_SIZE = (600, 800)`. |
| `server/trmnl-service.js:173-174` | The mock screen is 800×480, which is stale since the BYOS device became `amazon_kindle_7` (800×600). |
| `kindle/config/dashboard.conf` | The `BACKUP_IMAGE` contract says "must be a valid 600x800 grayscale PNG". |
| `server/dashboard-engine.js` `drawBatteryChip` | Assumes the 90° pre-rotation from BYOS's `amazon_kindle_7`. |

**Fix:** give `optimize-for-eink.py` `--size WxH`, defaulting to 600×800, and
turn the hard check into "matches the requested size". Everything else only
matters if the kitchen reuses the canvas stack, and the plan says it won't.

### F10 — The Kindle shell client assumes a Kindle Touch talking to the Pi

**Unverified** until someone has a shell on the Paperwhite. These are risks to
check, not confirmed bugs.

- **Framework job name.**
  - `dashboard-loop.sh:92-96` runs `/sbin/stop framework`.
  - `start.sh:261` and `stop.sh:210` gate on `/etc/upstart/framework`.
  - PW2-and-later firmware is widely reported to run its GUI as the upstart
    job `lab126_gui`. If `stop framework` fails on the PW3, the loop only logs
    "already stopped or not found", and powerd keeps managing sleep. That is
    the failure CLAUDE.md's "persistent loop instead of cron" section
    describes.
  - A permanent charger probably makes it harmless. Check with
    `initctl list | grep -iE 'gui|framework'` before trusting it.
- **ICMP pre-check.**
  - `fetch-dashboard.sh:256-262` pings the server first, and a failed ping
    aborts the fetch. That is fine for the Pi.
  - If the kitchen fetches from the **Mac**, macOS firewall "stealth mode"
    drops ICMP, and every fetch would fail before any HTTP is attempted.
  - Make the ping advisory, or delete it; the `/health` probe already covers
    reachability.
- **`/health` coupling.** `:268` requires `GET /health` on whatever server is
    configured. The Mac render service must implement it, or F6 option (a)
    has to be chosen.
- **Refresh flashing.**
  - Each update does `eips -c`, then `eips -f -g` twice (`:452-470`), which is
    three flashes.
  - At 300 ppi in a kitchen this is a design decision to make on purpose, not
    something to inherit.
  - On the PW3, FBInk (`fbink -g file=... -W GC16`) gives better waveform
    control than `eips`, and KUAL packages ship it.
- **`gasgauge-info` and `isCharging`.** Still worth sending from the kitchen:
  its profile has battery off, so they cost nothing and help diagnose "the
  charger got unplugged".

### F11 — Transit countdowns can be up to about 28 minutes old

- `transit-service.js:177-179` computes train minutes against
  `raw.ctatt.tmst` whenever `nowMs` is omitted, and `getTransitData` (`:232`)
  always omits it.
- On `expired-cache` (the API down for hours), trains that left hours ago show
  as "4m". Bus `prdctdn` is relative by definition, so it has the same
  problem.
- **Even when healthy,** the countdown shown on the wall has passed through
  every stage below. Adding them up, worst-case age at display is about
  28 minutes:

  | Stage | Up to |
  |---|---|
  | Pi transit cache (`TRANSIT_CACHE_TTL_MS`) | 5 min |
  | BYOS poll (`refresh_interval: 5`) | 5 min |
  | Pi TRMNL cache (480 s) | 8 min |
  | Kindle `UPDATE_INTERVAL` (600 s) | 10 min |

  The `cta/quadrant.liquid` tile shows only `{{ a.minutes }}m`, with no
  as-of time.
- **Fix:**
  - Compute against `Date.now()` for `api`/`cache` and drop arrivals that are
    already past.
  - Ship each arrival's absolute time (`arrT`, or the bus `prdtm`) plus a
    top-level `asOf`.
  - Have the recipe show a clock time ("8:42") next to or instead of the
    countdown.

### F13 — `weather-service.js`: UTC "today", mock data in production, host-timezone labels

## Low

### F14 — Cache-key cardinality is unbounded

- `getCacheKey` (`local-dashboard-server.js:179-191`) keeps every query
  parameter except `battery`, `charging` and `t`.
- `DeviceAlertRegistry.get` (`device-alerts.js:105-139`) creates a Map entry
  for any id that matches `[a-z0-9_-]{1,32}`.
- So `/dashboard?device=a1…aN` or `?x=1…N` means N full renders plus N Python
  subprocesses on the Pi, which is also the household Pi-hole, and unbounded
  Map growth.
- The exposure is LAN-only, but something on the LAN that prefetches links
  (see F15) can trigger it by accident.
- **Fix:** allowlist the cache-key parameters (`layout`, `device` if known,
  `grid`), and cap unknown device ids. Anything unrecognised should go into
  one shared `unknown` bucket.

### F15 — `/next` changes state on a GET

- `local-dashboard-server.js:582-584` routes `/next` with no method check and
  no confirmation.
- Anything that fetches the URL advances the playlist. Examples are iMessage
  link previews (generated on the sender's device, on the LAN) and browser
  prefetch.
- Discord's own unfurler can't reach a LAN IP, so the Discord ideas are safe
  as long as the link isn't proxied.
- **Fix:** have GET show a button page, and let a POST (or
  `GET /next?go=1` from that page) do the advance.

### F16 — Alerting has no watchdog, and Discord posts have no timeout

- `notify.js:24` calls `https.request` without a `timeout`, so a hung Discord
  endpoint leaks a socket per alert.
- More important: the Discord alerts that report a dead Kindle run inside the
  same Node process as `/dashboard`. A crash-looping server (see F4) is
  silent.
- **Cheapest fix:** a `systemd` `OnFailure=` unit that curls the webhook,
  since the Pi already has `curl`. Alternatively, have the Mac's launchd poll
  the Pi's `/health` and post when it fails. It already hosts BYOS and the
  LLM jobs.

### F17 — Six hand-copied cache→fallback chains

- `transit`, `todoist`, `fitness`, `rss`, `calendar` and `weather` each
  reimplement `isCacheValid`, `loadCachedData`, `saveCachedData` and the
  fallback chain.
- They have drifted:
  - The expired-cache label is `expired-cache` in some and `cache_expired` in
    `weather-service.js:240`.
  - Weather returns `mock_fallback`.
  - Calendar puts the label in `_source`, the others in `source`.
- Cache writes use `writeFileSync` directly, which is not atomic. A crash
  mid-write leaves a corrupt file, `loadCachedData` returns `null`, and the
  chain falls through to the **fixture**. Combined with F3, a power cut can
  put made-up data on the wall.
- **Fix:** before adding horoscope, steps and agenda (three more copies),
  extract `cached-source.js`. Its job is `get({ fetch, parse, fixture, ttl })`,
  writing to a temp file and then renaming. `trmnl-service.js:153-154`
  already does the temp-and-rename. The horoscope spike in this PR follows the
  existing pattern, so it stays consistent until then.

### F19 — Dead code, with one important caveat

The native portrait stack isn't referenced by any playlist or layout in use,
but **it isn't fully dead**. In `resolveLayout`
(`local-dashboard-server.js:215-220`), when BYOS has no screen (neither fresh
nor cached), `/dashboard` falls back to `config.DEFAULT_LAYOUT`, which is
`wild-swiss`. That happens on a cold start with an empty
`cache/trmnl/screen.png`.

That fallback renders **portrait** content. On the planned landscape-mounted
Kindle it would read sideways. The fallback exists, but it is already wrong for
where the hardware is heading.

| Code | Size | Only used by |
|---|---|---|
| `dashboard-engine.js`: every component except `TrmnlComponent`, `GridSystem` and the registry | ~1,100 lines | native layouts |
| `pokemon-service.js`, `pokemon-selector.js`, `build-pokemon-db.js`, `optimize-sprite-for-eink.py`, `pokemon-data.json` | ~990 lines plus 108 KB of JSON | native layouts |
| `render-utils.js`, `quotes.json` | ~110 lines | native layouts |
| `layouts/*.json` except `trmnl.json` | 10 files | native layouts / the `?layout=` override |
| `generate-and-test.sh`, `watch-and-update.sh` | ~580 lines | referenced only by each other; both predate TRMNL |
| `weather-service.js` | 320 lines | native layouts. **Keep it**: the kitchen plans to reuse it (after F13). |
| `TRMNL_SLOT_MINUTES`, `alternate` mode | — | not used under `TRMNL_MODE=only`, but a supported mode |
| `handleApiTransit` | 12 lines | duplicates `handleApiJson` |
| `dashboard-loop.sh:186-189` | 3 lines | `first_sunday`/`last_sunday` are computed and never read |

**Recommendation**
1. Replace the `wild-swiss` fallback with a one-component *landscape* "BYOS
   unreachable — last update HH:MM" layout. That takes a few dozen lines
   instead of about 2,700.
2. Tag the current state (`git tag native-stack-2026-09`) so it can be
   recovered, then delete the Pokemon and native-component code in its own
   PR.
3. The kitchen won't use node-canvas (HANDOFF: `bug_eink_local_canvas_rendering_broken`),
   so nothing downstream needs this code.

Don't combine the deletion with feature work; it is easy to review on its own.

## Multi-device readiness checklist

This is what has to be true before the Paperwhite ever polls. Each item is
ordered by what it depends on.

1. The client sends its identity (F1). Needs `DEVICE_ID` in the conf, a
   kitchen conf file, and a key-auth deploy.
2. The kitchen's fetches reach the Pi's registry (F6). Proxy or heartbeat;
   the Pi proxy is recommended.
3. Per-device active hours and threshold (F7), so the 05:30 start is
   monitored.
4. `/health` shows per-device `lastFetchAt` (F8). Without it there's no way to
   verify item 2 from a phone.
5. The optimizer accepts `--size 1072x1448` (F9), if the kitchen PNG is
   post-processed with it.
6. The shell client is verified on PW3 firmware (F10): framework job name, no
   ICMP gate, a 1072×1448 fallback image, and a decision on the refresh
   policy.
7. Only then add `kitchen` to `MONITORED_DEVICES`. This stays last, per the
   handoff.

The data side has two blockers for `/api/agenda`: F2 (recurring events) and
F5 (the UTC date).
